## Rollback

Every change is one commit in its own repo, revertible independently: daptin commits A–D revert via `git revert <sha> && bash build-local-image.sh && docker compose up -d` (image pinned by DAPTIN_IMAGE, daptin/docker-compose.yml:24); outer commits (docs revert, schema, docs pass) via `git revert`. No data migrations to undo — permission rows re-sync from schema YAML at boot (UpdateActionTable dbfunctions_update.go:819-826; UpdateWorldTable :1476-1490), so reverting schema_wallet.yaml alone restores prior behavior next boot. F2 crash-loop recovery: revert image; if needed, emergency DAPTIN_SKIP_INITIALISE_RESOURCES=true boot (now loudly warned — money writes unavailable in that mode); post-fix a Fatalf means a genuine postgres statement failure — re-apply the two CREATE TRIGGER statements by hand via psql (temporary, non-authoritative per 0003) and file an incident. Wallet-503-after-rollback recovery is written into docs/RUNBOOK.md by Step 6(f)/Step 10(c): check postgres health → run the gate query (to_regclass NULL = tables gone) → restore from backup if one exists (only ledger-history-preserving path) → otherwise reboot with schema mounted, record a balance-loss incident, and never re-credit by direct SQL (violates §42.3); compensate via wallet_credit. The boot gate itself is the recovery checkpoint: nothing is 'recovered' until both trigger assertions pass.

## Residual risks

- RANK 1 — Host/superuser psql can still DROP TRIGGER, forge INSERTs (mint wallets, forge ledger rows), UPDATE wallets between boots. Unchanged 0006 residual; uncloseable in this package (credential custody). This fix set SHRINKS the in-run daptin paths to that state but does not close it.
- RANK 2 — CLASS SHRUNK, NOT CLOSED: future raw-SQL / DirectInsert performer. The app-layer denylist closes the known sites; a future performer would bypass again. Mitigation is the upgraded 0006 extension rule PLUS the machine-checked source-scan tripwire — a convention enforced by CI, not a structural impossibility.
- RANK 3 — wallets UPDATE has no DB-layer barrier (financial_guard.go:48-50, deliberate per 0006): any future code path holding a *sqlx.Tx can edit balances. All known surfaces refuse post-remediation; the tripwire narrows entry points; the DB does not enforce.
- RANK 4 — INSERT on both money tables is trigger-uncovered: a mint (wallets INSERT) or forgery (wallet_ledger INSERT) lands if it evades the app-layer checks. Only the host/DB boundary or future DB-layer work (e.g. a requires-fresh-ledger-row constraint in the Phase 1 state machine) can close this.
- RANK 5 — $transaction refusal is lexical, not parsed: a query routing around the literal table names defeats FinancialSQLRefuses. Accepted and documented; false positives fail closed (a quoted literal naming 'wallets' gets a 403 — harmless, tested).
- RANK 6 — Execute-gate coarseness persists: with AuthenticatedExecute, ANY signed-in user can debit any wallet whose reference_id they know. Ownership/entitlement shaping is product policy, explicitly out of scope; F1 only removes the anonymous principal.
- RANK 7 — Legacy NULL-owner rows (id=6) remain anon-PEEKABLE: CanPeek owner-matches NullReferenceId (permission.go:216-221, NullReferenceId guarded only in CanExecute at :69). Rows are dead (balance 0, no ledger), preserved as evidence, and undeletable by the trigger. Fixing CanPeek is a shared-contract change touching every daptin caller — rejected per 0001.
- RANK 8 — Guard presence is boot-observable only: an operator dropping triggers via psql mid-run is caught at the next gate run. F4 removes daptin's own paths to that state; continuous monitoring accepted as out of scope under 0003's rebuild model.
- RANK 9 — File modes (0644) are not git-tracked: a fresh Linux clone can reintroduce 0600; mitigated only by the RUNBOOK note.
- RANK 10 — The DELETE-outcome middleware widening is latent (no schema action carries a DELETE outcome on any table today, reviewer-verified) and rebase-sensitive: if upstream removes the AdministratorGroupId append at handle_action.go:401-404, or restructures the outcome switch, the pre-switch check must be re-placed. Named in the 0006 amendment.
